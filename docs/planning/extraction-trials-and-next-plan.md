# 입학요강 추출기 Trial & Error 회고 및 향후 대응 계획

- 작성일: 2026-08-13
- 대상 프로젝트: Admission Extension
- 문서 목적: 이번 개발 세션에서 시도한 접근, 실패 원인, 확인된 성과와 한계를 기록하고 이후 구현의 판단 기준을 고정한다.

## 1. 결론 요약

이번 세션에서 확인한 핵심은 다음과 같다.

1. 75개 학교의 웹사이트에 공통 패턴이 전혀 없는 것은 아니다.
2. 다만 초기 앱이 찾으려던 패턴은 주로 제목과 본문 문자열이었고, 실제로 보존해야 했던 패턴은 표의 행·열, 제목과 다음 요소, `dt`와 `dd`, 카드의 부모·자식, 숨겨진 탭, 국가 선택 결과 같은 DOM 관계였다.
3. KCL처럼 정보가 한 페이지에 명확히 펼쳐진 학교를 초기 기준으로 삼으면서, 평면 텍스트만으로도 다른 학교를 처리할 수 있다는 잘못된 낙관이 생겼다.
4. Entry Requirements는 실제 실패 사례를 DOM 후보와 경계 문제로 다시 정의한 뒤 범용 로직으로 여러 학교를 함께 해결할 수 있었다. 이는 구조 패턴을 제대로 잡으면 학교별 예외를 줄일 수 있다는 증거다.
5. Tuition Fee는 문장형 테스트 데이터에서는 성공했지만 실제 페이지에서는 금액과 의미가 서로 다른 DOM 요소에 있어 실패했다. 테스트 통과가 실사용 성공을 보장하지 못한 이유도 여기에 있다.
6. 따라서 전체 앱을 폐기하거나 15개 학교를 각각 완전히 별도 구현하는 대신, **추출 계층만 구조 보존형 v2로 교체**하는 것이 적절하다.
7. 범용 최소 기능의 정의도 바꾼다. 미지의 학교에서 완전 자동 추출을 강제하는 대신, 자동 후보가 실패하면 사용자가 원문에서 한 번 선택하여 값·근거·학년도·확인일을 저장할 수 있어야 한다.

즉, 앞으로의 제품 목표는 다음 두 가지다.

- 자주 쓰는 학교와 반복 구조에서는 자동 추출과 복사를 최대한 빠르게 한다.
- 자동 추출이 실패해도 원문 선택과 확인 이력 저장을 통해 반복 확인과 기억 부담을 줄인다.

## 2. 최초 문제와 목표

실제 업무 조건은 다음과 같았다.

- 익숙하고 DB가 갖춰진 학교는 학과 하나를 확인하는 데 10분이 채 걸리지 않는 경우가 많다.
- 처음 보는 학교는 사이트 구조를 파악하는 데 90~120분이 걸릴 수 있고, 이후 2~3회까지 같은 경로에서 다시 헤맬 수 있다.
- 업무의 대부분은 영국 학교지만, 가끔 들어오는 호주 학교처럼 기존 앱이 거의 아무것도 인식하지 못하는 경우가 있다.
- 72개 학교 DB가 있어도 사이트 구조를 모르면 그 자산을 바로 활용하기 어렵다.

초기 제품 목표는 “미지의 학교에서도 최소 기능이 작동하는 범용 앱”이었다. 이를 위해 먼저 적당히 작동하는 버전을 실무에 투입하고, 막히는 사례를 모아 범용성을 넓히려 했다.

이 방향 자체는 타당했다. 문제는 당시의 “적당히 작동한다”는 기준이 너무 낮았고, 실패를 관찰할 수 있는 진단 정보와 안전한 수동 fallback이 충분하지 않았다는 점이다.

## 3. Trial & Error 과정

### 3.1 소수의 모범 학교를 기준으로 한 초기 구현

초기 코드는 KCL, QMUL·Queen Mary, Manchester 등 소수 학교를 기준으로 만들어졌다. 이 학교들에서는 제목과 본문 텍스트가 비교적 명확했고, 특히 KCL은 학비가 별도 페이지에 있다는 점을 제외하면 주요 정보가 페이지에 잘 펼쳐져 있었다.

#### 결과

- 기준 학교에서는 비교적 잘 작동했다.
- 미지의 학교, 특히 호주 학교에서는 수집 결과가 0~2개 수준까지 떨어졌다.
- Manchester도 경영대의 섹션 분리형 페이지에서는 잘 작동하지만 공대의 단일 페이지형 구조에서는 Korean Equivalent, Tuition Fee, Staged Admission, Reference, SOP, CV 조건 등을 놓쳤다.

#### 배운 점

- 학교 이름이 같아도 단과대나 사이트 템플릿에 따라 구조가 달라질 수 있다.
- “학교별 지원”만으로는 충분하지 않고, 한 학교 안의 여러 템플릿도 고려해야 한다.
- 모범적인 사이트를 기준으로 만든 성공은 범용성의 증거가 아니었다.

### 3.2 자주 쓰는 학교 15개 집중 전략

전체 72~75개 학교를 전수 지원할지, 자주 쓰는 10~15개 학교를 먼저 지원할지, 문제가 일정량 모일 때마다 수정할지를 검토했다.

업무 빈도 자료에서 상위권 학교는 KCL 41회, Manchester 41회, Leeds 36회, UCL 25회, Warwick 25회, Edinburgh 24회, Birmingham 21회, York 18회, Bristol 17회, Queen Mary 16회, Nottingham 14회, Exeter 13회, SOAS 13회, Loughborough 12회, Southampton 12회였다. 이 상위 15개만 합쳐도 약 328건이다.

#### 결정

- 72~75개 전체를 동일한 수준으로 지원하지 않는다.
- 우선 빈도가 높은 학교에서 반복되는 문제를 해결한다.
- 다만 학교마다 독립 수집기를 복제하기보다, 여러 학교에서 재사용할 수 있는 구조 패턴을 먼저 찾는다.

### 3.3 Entry Requirements 과다 수집 문제

Edinburgh를 포함한 여러 학교에서 Entry Requirements가 해당 섹션만 가져오는 대신 페이지 전체에 가까운 내용을 수집했다. 국가 선택 드롭다운의 모든 국가명까지 포함되기도 했다.

반대로 UCL 사례에서는 원문이 계속 이어지는데도 `A minimum of an upper second-class UK bachelor's degree (or`에서 잘리는 문제도 있었다.

#### 처음의 대응

- 특정 제목과 종료 문구를 추가했다.
- 잘림과 과다 수집을 개별 사례로 좁혀 수정했다.

#### 전환점

과다 수집된 10개 학교의 DOM 구조를 비교하고, 학교명이 아니라 실패 계열로 묶는 실험을 진행했다. Manchester, Edinburgh, Leeds, Birmingham, Nottingham, Bristol, York, Loughborough, Southampton, Exeter 등의 사례를 후보 생성, 경계 판정, 제외 요소의 문제로 재구성했다.

#### 결과

- Entry Requirements v2는 하나의 큰 텍스트 블록을 가져오는 대신 여러 후보 범위를 만든 뒤 점수와 경계를 비교하도록 바뀌었다.
- 국가 목록, 내비게이션, 관련 없는 섹션을 제외했다.
- 괄호나 인라인 요소 때문에 문장이 중간에 잘리는 문제를 보완했다.
- J님이 CSV에 정리한 학교들에서 Bristol, Loughborough, Birmingham을 포함해 Entry Requirements가 잘 수집되는 것을 확인했다.

#### 배운 점

“패턴이 없는 것이 패턴”이라기보다, 처음에 잘못된 층위에서 패턴을 찾고 있었다. 문구는 제각각이어도 섹션 후보, DOM 경계, 제외 영역이라는 구조 패턴은 재사용할 수 있었다.

### 3.4 UCL, Warwick, Sheffield 집중 보완

상위권 학교를 중심으로 실제 업무에서 막히는 문제를 순차적으로 보완했다.

- UCL: 학비의 잘못된 숫자 £350 제거, 비자 불필요 마감일 제외, IELTS level 중심 표시, South Korea 선택 처리
- Warwick: South Korea 표현과 드롭다운 처리, 별도 학비 경로 추적, Entry Requirements 재보완
- Sheffield: 주요 필드 수집 및 지원 서류의 `not required` 판정
- 공통 UI: 중복된 근거 본문을 제거하고 `[원문 열기]`를 `[원문 보기]`로 변경, 클릭 시 좌측 페이지의 근거 위치에 포커스
- 안정성: 근거 객체가 `null`일 때 `source.url`을 읽어 발생한 오류 수정

#### 배운 점

- 정확한 원문 위치로 이동하는 기능은 추출 결과를 신뢰하고 검토하는 시간을 줄인다.
- IELTS처럼 별도 등급 체계를 쓰는 항목은 모든 점수 문장을 복사하기보다 Level A/B/C, Level 1/2/3, B1/B2 같은 분류를 먼저 보여주는 편이 실제 작업 방식에 맞다.
- 자동화의 가치는 필드를 많이 채우는 데만 있지 않고, 검토와 복사를 빠르게 만드는 데도 있다.

### 3.5 Tuition Fee 금액 크기 가설 검토

초기에는 페이지에서 가장 큰 금액이 학비이고 가장 작은 금액이 지원비일 가능성이 높다는 단순 규칙을 검토했다.

13개 학교의 실제 금액 문맥을 조사한 결과 이 규칙은 안전하지 않았다.

- Manchester: 전체 지원 재원 £300,000이 학비 £38,400보다 큼
- Birmingham: 지원 재원 £33m이 학비보다 큼
- Loughborough: 시설 투자액 £17m이 학비보다 큼
- Southampton: 연봉 예시 £50k가 학비보다 큼
- Exeter: 장학 재원 £7m이 학비보다 큼
- 작은 금액은 지원비가 아니라 보증금, Home fee, 기타 비용일 수 있음

#### 결정

금액 크기는 학비 판정의 주 기준으로 사용하지 않는다. 먼저 주변 문맥으로 학비, 지원비, 보증금, 장학금·할인, 기타 비용을 분류한 뒤 학년도, 과정, Full-time·Part-time, Home·International 조건을 적용한다.

### 3.6 학년도 정규화와 금액 문맥 분류 구현

사용자가 설정한 `2026/27`과 페이지의 `2026-27`, `2026`, `September 2026` 같은 표기를 연결하는 로직과 금액 문맥 분류를 구현했다.

문장형 fixture를 사용한 13개 학교 회귀 테스트와 전체 검사 92개가 통과했다.

#### 실제 사용 결과

- Exeter, York, Birmingham: 페이지에 학비가 있는데 못 찾음
- Southampton, Sheffield: 학비 대신 보증금 등 다른 금액이 표시됨
- Loughborough, Bristol, Nottingham: 숫자는 찾았지만 학년도 일치에 실패
- UCL, Manchester: UK와 International fee가 함께 표시됨

#### 배운 점

테스트는 통과했지만 fixture가 실제 DOM을 지나치게 단순화했다. 테스트 문장에는 `International tuition fee 2026/27 £...`처럼 라벨, 연도, 금액이 한 덩어리로 있었지만 실제 사이트에서는 이 정보가 여러 요소와 부모 컨테이너에 분산돼 있었다.

따라서 이 단계의 실패는 분류 규칙을 조금 더 추가하면 끝나는 문제가 아니라, 입력 데이터가 DOM 관계를 잃은 상태라는 구조적 문제였다.

### 3.7 실제 DOM 재검사에서 확인한 실패 계열

실제 페이지를 다시 확인한 결과, 학교별 무작위 예외처럼 보이던 문제는 다음 구조 계열로 묶였다.

| 구조 계열 | 대표 학교 | 현재 실패 원인 |
| --- | --- | --- |
| 표의 행·열 | York, Nottingham, Warwick, Edinburgh | 금액은 읽지만 열 제목인 Home·International 의미를 잃음 |
| 정의 목록 `dt`·`dd` | Bristol | `dd`의 금액만 읽고 대응하는 `dt` 라벨을 잃음 |
| 카드와 부모 컨테이너 | Sheffield, Loughborough | 자식의 금액과 부모의 학년도·fee status를 연결하지 못함 |
| 제목과 다음 형제 요소 | Exeter | `International fees per year` 제목과 다음 금액 문단을 별개로 처리함 |
| 한 문장 안의 순서 관계 | Manchester | 첫 금액 뒤에 나오는 International 라벨을 잘못 연결할 수 있음 |
| 숨겨진 탭·tabpanel | Southampton | 화면상 탭 내부 콘텐츠를 일반 수집 범위에서 놓치거나, deposit 문맥을 tuition으로 오판함 |
| 국가 선택 후 동적 결과 | Birmingham, UCL, Warwick | South Korea 선택 전 기본 UK 결과를 읽거나, 양쪽 결과를 함께 읽음 |
| 공식 연결 학비 페이지 | KCL, Edinburgh, Warwick | 과정 코드와 학년도를 유지한 링크 추적이 필요함 |
| 복수 학년도 | Loughborough 등 | 금액이 속한 카드의 학년도를 보존하지 않으면 페이지 전체 연도로 확정 불가 |

추가로 공통 `collectSection()`이 Entry Requirements용 종료 패턴을 Fee 섹션에도 재사용하면서 `fees`, `tuition fees` 자체를 종료 신호로 보고 학비 섹션을 잘라내는 결함도 확인했다. 섹션 수집 규칙은 필드별로 분리해야 한다.

Nottingham의 경우 페이지 자체가 September 2027 입학과 2027년 학비를 안내하고 있어, 사용자 기준이 2026/27이라면 불일치 경고가 맞다. 모든 경고가 추출 오류인 것은 아니며, 실제 페이지의 입학 주기와 사용자 기준을 구분해야 한다.

## 4. 무엇을 유지하고 무엇을 교체할 것인가

### 유지할 부분

- Side Panel UI와 필드 순서
- 분석 기준 입력과 저장
- `[원문 보기]` 및 페이지 포커스 기능
- 사용자가 확인한 결과와 날짜를 저장하는 기반
- KCL, QMUL 등 이미 정확히 동작하는 전용 처리
- 사이트 registry와 연결 페이지 추적 기반
- Entry Requirements v2의 후보·경계 방식

### 교체할 부분

- 페이지를 먼저 평면 텍스트로 만든 뒤 의미를 추정하는 generic 추출 핵심
- Entry Requirements 종료 규칙을 다른 필드에 공용으로 적용하는 방식
- 금액과 가장 가까운 단어만으로 학비 유형을 결정하는 방식
- 실제 DOM 관계를 생략한 문장형 fixture 중심 테스트
- 자동 확정과 사용자 확인 필요 상태의 경계가 불분명한 부분

전체 앱을 처음부터 다시 만드는 것은 비용 대비 이점이 작다. UI, 저장, 원문 포커스, 이미 동작하는 리더는 유효하다. **추출 계층과 테스트 입력만 v2로 교체**하는 것이 가장 작은 범위의 근본 수정이다.

## 5. 변경된 제품 목표

### 5.1 자동 추출 모드

앱이 DOM 관계를 보존한 후보를 만들고, 사용자의 학년도·입학 월·수학 형태·fee status 기준과 정확히 맞는 경우에만 결과를 자동 확정한다.

### 5.2 보조 수집 모드

자동 확정이 어렵거나 미지의 학교인 경우 다음 흐름을 제공한다.

1. 앱이 가능한 후보와 원문 위치를 보여준다.
2. 후보가 없으면 사용자가 페이지에서 필요한 문장이나 금액을 직접 선택한다.
3. 선택한 값, 원문 URL, 원문 위치, 적용 학년도, 확인일을 저장한다.
4. 다음 방문에서는 이전 확인일과 기준을 눈에 띄게 보여준다.

이 모드의 목표는 “미지의 학교도 완전 자동으로 이해”하는 것이 아니라, **실패해도 10초 안에 수동 수집을 끝내고 같은 확인을 반복하지 않게 하는 것**이다.

## 6. Extraction v2 설계 원칙

새 추출 계층은 다음 순서로 동작한다.

1. **페이지 준비**: 필요한 탭을 열고, 국가 선택이 필요한 사이트에서는 South Korea 결과를 요청하며, 공식 학비 링크가 있으면 추적한다.
2. **구조 보존 snapshot 생성**: 텍스트뿐 아니라 요소 종류, 부모 제목, 이전·다음 형제, 표의 행·열 제목, `dt`·`dd` 관계, 숨김 상태, 링크, class와 주요 attribute를 보존한다.
3. **구조별 extractor 실행**: table, definition list, card, heading+sibling, ordered sentence, hidden tab, linked page 전략을 각각 적용한다.
4. **의미 분류**: 학비, 지원비, 보증금, 장학금·할인, 생활비·기타를 구분한다. deposit이나 application fee 문맥은 같은 블록에 tuition이라는 단어가 있어도 우선 제외한다.
5. **기준 매칭**: 학년도·입학 시기·Full-time·Part-time·Home·International을 후보가 속한 구조 안에서 연결한다.
6. **신뢰도 판정**: 값, 기준, 근거 위치가 모두 명확할 때만 자동 확정한다.
7. **수동 fallback**: 불확실하면 추측값을 확정하지 않고 원문 선택과 확인 이력 저장으로 전환한다.

학교별 처리는 완전한 별도 수집기가 아니라 다음과 같은 얇은 profile로 제한한다.

- 어떤 구조 extractor를 우선할지
- South Korea 선택 컨트롤과 결과 갱신 조건
- 기본으로 열어야 하는 탭
- 공식 학비 링크를 찾는 방법
- 같은 학교의 여러 템플릿 식별

## 7. 상위 학교 지원 전략

### 7.1 15개 완전 독립 수집기는 만들지 않는다

15개 학교마다 모든 필드의 수집 코드를 복제하면 당장은 빨라 보여도 사이트 변경 시 15개 코드를 각각 유지해야 한다. 대신 6~8개의 구조 extractor를 만들고, 상위 학교에는 필요한 profile만 붙인다.

정말 독자적인 사이트만 제한적으로 전용 reader를 사용한다.

### 7.2 모든 필드를 같은 깊이로 자동화하지 않는다

우선순위는 실제로 시간을 많이 쓰거나 짜증이 큰 항목을 기준으로 한다.

1. Tuition Fee
2. Korean Equivalent
3. Application Deadline·Staged Admission
4. Entry Requirements
5. Reference, SOP, CV 등 지원 서류
6. IELTS level과 세부 기준 링크

이미 안정화된 Entry Requirements는 회귀를 막는 수준으로 유지하고, 다음 구조 개편의 첫 대상은 Tuition Fee로 한다.

### 7.3 ROI 기준

빈도 상위 15개 학교는 약 328건의 연간 작업량을 차지한다. 건당 2분만 줄여도 약 11시간, 건당 5분을 줄이면 약 27시간을 절약한다.

따라서 상위 학교를 지원할 가치는 있다. 단, 목표는 모든 필드의 완전 자동화가 아니라 다음 세 가지다.

- 클릭을 여러 번 해야 하는 학비·국가별 기준 접근을 줄일 것
- 반복 복사를 줄일 것
- 과거 확인 여부와 확인 날짜를 기억할 필요가 없게 할 것

## 8. 구현 단계

### Phase 0. 현재 상태 고정과 실측 benchmark

- 현재 동작하는 기능과 실패 사례를 구분해 snapshot으로 보존한다.
- 기존 13개 문장형 fixture는 보조 테스트로 남기되, 실제 성공 증거로 간주하지 않는다.
- 대표 학교의 실제 DOM 조각을 개인정보 없이 fixture로 저장한다.
- 같은 학교에 템플릿이 둘 이상이면 최소 2개 학과를 확보한다.

### Phase 1. Tuition Fee 구조 보존형 v2

다음 대표 구조를 우선 구현한다.

- York: 표의 열 제목과 금액 연결
- Bristol: `dt`·`dd` 연결
- Loughborough: 부모 카드의 학년도와 자식 금액 연결
- Exeter: 제목과 다음 형제 문단 연결
- Southampton: 숨겨진 탭과 deposit 우선 제외
- Birmingham: 국가 선택 후 갱신된 결과 확인
- Edinburgh·Warwick: 공식 연결 학비표와 과정 코드 유지
- UCL·Manchester: UK와 International의 순서·class 구분

### Phase 2. 공통 페이지 준비와 학교 profile

- 탭 열기, 국가 선택, 비동기 결과 대기, 연결 페이지 추적을 공통 인터페이스로 만든다.
- 학교 profile에는 selector 전체를 복제하지 않고 준비 동작과 구조 우선순위만 둔다.
- Manchester처럼 한 학교에 복수 템플릿이 있는 경우 URL·DOM 특징으로 profile을 나눈다.

### Phase 3. 수동 선택과 확인 이력 강화

- 페이지에서 선택한 텍스트를 현재 필드 값으로 가져오는 기능을 제공한다.
- 저장 시 URL, 원문 위치, 학년도, 입학 월, 확인일을 함께 기록한다.
- Side Panel 상단 또는 각 필드에 `마지막 확인: YYYY-MM-DD`와 당시 기준을 표시한다.
- 페이지 내용이나 사용 기준이 달라졌을 때만 재확인이 필요하다는 상태를 보여준다.

이 단계는 자동 추출이 모두 끝난 뒤의 부가 기능이 아니라, 미지의 학교에서 즉시 ROI를 만드는 핵심 기능으로 앞당긴다.

### Phase 4. 상위 학교 실사용 회귀

- 각 학교에서 최소 2개 학과를 확인한다.
- 코드 테스트뿐 아니라 실제 설치된 Chrome 확장을 다시 로드한 상태에서 검증한다.
- 결과값만 보지 않고 `[원문 보기]`, 학년도, International 여부, 과정 형태, 확인일 저장까지 확인한다.
- 실패는 학교명이 아니라 table, card, dynamic country 같은 구조 계열에 추가한다.

### Phase 5. 확대 여부 결정

구조 extractor 6~8개와 소수 profile로 상위 15개 중 최소 12개가 안정적으로 동작하는지 평가한다.

- 기준을 충족하면 다음 빈도 구간의 학교로 확대한다.
- 기준을 충족하지 못하면 범용 완전 자동화 확대를 중단한다.
- 이 경우 제품을 `자동 후보 + 수동 선택 + 확인 이력` 도구로 고정하고, 특별히 ROI가 큰 학교만 전용 지원한다.

## 9. 테스트 원칙

앞으로 테스트 통과와 실사용 성공을 혼동하지 않도록 다음 원칙을 적용한다.

1. 실제 DOM 관계를 보존한 fixture를 사용한다.
2. 표 테스트는 행·열 제목을, 정의 목록은 `dt`·`dd`를, 카드는 부모 제목과 자식 값을 그대로 포함한다.
3. 학비 테스트는 정답 금액뿐 아니라 다음 오답이 선택되지 않는지도 검증한다.
   - Home fee
   - deposit
   - application fee
   - scholarship·discount
   - 생활비·시설 투자비·연봉
   - 다른 학년도 금액
4. 값과 함께 source, academic cycle, fee status, study mode를 검증한다.
5. 사이트별 최소 2개 학과로 템플릿 차이를 확인한다.
6. `코드 회귀 테스트 통과`, `로컬 빌드 통과`, `설치된 Chrome 확장에서 확인`을 별도 상태로 기록한다.
7. 확신이 없는 결과를 채우는 것보다 `확인 필요`로 남기는 것을 성공으로 본다.

## 10. 중단 기준과 비목표

### 중단 기준

- 새로운 실패를 고칠 때마다 재사용 가능한 구조 계열이 아니라 학교명 조건만 계속 늘어나는 경우
- 상위 15개 중 12개 안정화 기준을 충족하지 못하는 경우
- 절약 시간보다 유지·검증 시간이 지속적으로 큰 경우
- 자동 추출이 수동 확인보다 신뢰하기 어려워 재검토 시간을 더 늘리는 경우

### 현재 비목표

- 72~75개 학교의 모든 필드를 완전 자동화
- AI가 근거 없이 여러 후보 중 하나를 임의 확정
- 모든 학년과 Home·International 금액을 한꺼번에 표시
- 학교별 전체 코드를 15벌 이상 복제
- 사이트 변경을 영구적으로 예측하는 무유지보수 수집기

## 12. 최종 의사결정 기록

- 초기 설명이 부족해서 프로젝트가 실패한 것으로 보지 않는다. 실제 업무 문제는 충분히 설명됐고, 구현 단계에서 샘플 편향과 평면 텍스트 중심 설계를 더 일찍 의심하지 못한 것이 주요 원인이다.
- 기존 앱 전체를 폐기하지 않는다. 유효한 UI와 저장·검토 기능은 유지하고 추출 계층만 교체한다.
- 15개 학교를 각각 완전히 별도 구현하지 않는다. 구조 extractor와 얇은 학교 profile의 혼합 구조를 사용한다.
- 미지의 학교에서의 성공 기준은 완전 자동 추출이 아니라 빠른 수동 선택과 확인 이력 보존까지 포함한다.
- 앞으로의 ROI는 “자동으로 채운 필드 수”가 아니라 “실제 작업 시간, 클릭 수, 반복 확인과 기억 부담을 얼마나 줄였는가”로 평가한다.

## 13. Tuition Fee v2 구현 착수 결과

- 구현일: 2026-08-13
- 조사 범위: 영국 69개교, 호주 13개교, 총 82개교와 88개 과정 표본

DOM 전수 조사 결과, 계획 당시 예상했던 6~8개보다 적은 다음 4개 핵심 extractor 계열로 수렴했다.

1. `Table/Grid`
2. `Key-value/Definition`
3. `Card/Container`
4. `Heading/Sibling/Text`

국가·fee status·학년도·입학월 선택, accordion·tab·modal·지연 렌더, 공식 연결 fee 페이지, 미게시 상태, 복수 학년도는 별도 extractor가 아니라 공통 page adapter와 후보 상태로 처리한다. Manchester와 City St George처럼 복수 CMS가 확인된 학교만 URL·DOM 특징을 식별하는 얇은 template profile 대상으로 남긴다.

첫 구현에서는 기존 generic reader의 평면 금액 후보를 유지하되 우선순위를 낮추고, 다음 구조 후보를 먼저 만든다.

- 표: 열 제목, 행 제목, 셀 값을 한 후보 문맥으로 결합
- 정의 목록: `dt` 라벨과 다음 `dd` 값을 결합
- 카드: 학년도·audience 제목과 가장 작은 금액 자식 블록을 결합
- 제목형: fee 제목부터 다음 동급 제목 전까지 형제 요소를 순서대로 결합

금액 의미 분류에서는 가까운 `application fee`, `deposit`, `scholarship·funding`, 생활비·기타 비용 문맥을 tuition보다 우선 제외한다. Home·International과 학년도·입학 시기는 같은 구조 구간에서 찾고, 선택 어댑터가 실제로 활성화된 경우에만 선택된 fee status를 후보에 보완한다.

현재 구현 검증에는 York, Bristol, Loughborough, Exeter, Southampton, Birmingham, Manchester, St Andrews 구조와 별도 공식 fee 페이지 표본이 포함된다. 실제 DOM 관계를 보존한 fixture에서 구조 계열, 금액, 학년도, fee status, 수학 형태, 미게시 상태, 보증금·장학금 제외를 함께 검증한다.

남은 다음 단계는 설치된 Chrome 확장을 다시 로드한 뒤 대표 실제 페이지에서 검증하는 것이다. 특히 사이트에서 사용하는 custom select, modal, off-canvas처럼 표준 button·tab·select만으로 열리지 않는 제어는 실제 실패 URL이 확인될 때 재사용 가능한 adapter로 추가한다. 수동 원문 선택과 확인 이력 강화는 별도 UI 단계로 남아 있으며, 이번 구조 extractor 변경에는 포함하지 않았다.
